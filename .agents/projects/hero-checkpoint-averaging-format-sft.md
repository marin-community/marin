# Hero checkpoint averaging and format-SFT plan

Produce a Hero checkpoint that can reliably use the real Marin chat template, so subsequent RL task calibration measures task competence with fewer formatting failures. First establish a formatting and content baseline on the latest permanent 16K checkpoint. Evaluate offline LR-aware weight averaging as an independently gated candidate. Initialize selected chat output tokens from Will's single-token donors on the selected base, and prepare a bounded format-SFT pilot using LoRA plus selected vocabulary entries with a fresh optimizer.

This is an implementation and experiment handoff. The averaging and SFT have not run. Numerical pilot settings below are proposed starting points, not measured Hero recipes. The production pretraining run must continue unchanged. Launching a training run is a separate action from preparing this handoff.

## Execution stages and gates

1. Establish the baseline before preparing derived weights. Pin the latest permanent 16K checkpoint, tokenizer, evaluation backend and held-out panels. Evaluate the real Marin template and legacy PT serialization, retain failing generations, and classify termination, header, reasoning and tool failures. Record baseline loss, content variability and routing limits before selecting regression tolerances. If the baseline already passes the required interfaces and content gates, record that result before deciding whether SFT is needed.
2. Prove correctness on a small representative Hero configuration before full-model averaging or loading the full model into the new SFT path. Cover LR-aware averaging, donor initialization, weights-only restore, compact vocab deltas, adapter gradients, sharding and merge/export parity. Use the current Hero backend and preserve activation gradients through frozen layers. This backend integration is the main implementation risk.
3. Evaluate averaging independently. Inventory compatible checkpoints and verify their actual storage region. Run averaging workers and write the derived checkpoint in that same region. Compare the raw average against the latest PT checkpoint using predeclared loss, content and routing gates. Use the average as the SFT base only if it passes; otherwise use the latest PT checkpoint. Missing compatible snapshots or unavailable compute in the source region block averaging, while baseline-based SFT can proceed. Keep the reason and available averaging results in the record.
4. Once a training smoke is authorized, run a bounded one-rack LoRA-plus-vocab learning and throughput smoke. Measure memory, gradient behavior, token acquisition, update time and completed update counts. Select global batch, learning rates, inspection cadence and pilot budget from these measurements. A matched full-SFT throughput control is optional and must not delay the format experiment if it requires substantial extra implementation or unavailable memory.
5. Once the pilot is authorized and its configuration is pinned, run the bounded format-SFT pilot. Inspect at 16M non-padding tokens and cap the initial cycle at 64M unless the recorded smoke justifies a revised budget before launch. Set an earlier update-based inspection if needed. Stop when the formatting and content gates pass; diagnose loss, routing or nonfinite-value failures before further training. Export and validate ordinary Hero weights for downstream RL and serving.
6. Prepare a separate 65,536-position YaRN candidate E from merged format candidate D. Start with a configuration-only factor-4 extension of the 16K base; retain D separately. Verify native rotary numerics and export metadata, compare D/E on identical short and actual 16K panels, then evaluate E on actual prompts near 65K. Require serving parity and the predeclared content/loss/routing gates before downstream use. Any context-extension training is a separate measured intervention.

The stage order separates local correctness from full-model experiments. Baseline evaluation can use an existing validated evaluator; local correctness must pass before full-model I/O through newly implemented paths. Before any full-model I/O, record the durable artifact destination and execution placement. Training smokes and the pilot require separate launch authorization; this document update launches no jobs.

## Offline averaging and LR correction

For checkpoints theta_0 through theta_m in step order, define observed increments delta_i = theta_i - theta_(i-1). A convex checkpoint merge has the exact identity:

    theta_avg = sum_j c_j * theta_j
              = theta_0 + sum_i r_i * delta_i
    r_i = sum_(j=i..m) c_j
    c_0 = 1 - r_1
    c_i = r_i - r_(i+1)       (1 <= i < m)
    c_m = r_m

The coefficients r_i specify how much of each historical increment survives. Correct for Hero's changing LR through those increments; inverse-LR weights on snapshots do not implement this correction.

Proposed virtual cooldown: over the selected window [a,b], set `eta_target(t) = eta_actual(a) * (1 - (t-a)/(b-a))`. Reconstruct `eta_actual(t)` from the actual saved configuration and scheduler implementation, including its step convention. For interval i, approximate:

    r_i = sum_(updates in interval i) eta_target(t)
          / sum_(updates in interval i) eta_actual(t)

Checkpoint steps s_(i-1) and s_i bound the completed updates s_(i-1)+1 through s_i, inclusive. Determine from the pinned training loop whether completed update k uses scheduler index k-1 or another index; record and test that mapping against telemetry before computing sums. Apply the target LR at the corresponding update time, with the same convention.

This approximates a changed LR while holding each interval's update direction fixed. Verify `1 >= r_1 >= ... >= r_m >= 0`, hence nonnegative c_j summing to one. Fail on an incompatible target instead of silently clipping coefficients. Emit the actual and target LR curves, interval boundaries, ratios and final snapshot coefficients. Match reconstructed LR against logged samples at several steps.

The inspected run used a linear schedule, `num_train_steps=390251`, warmup fraction 0.01, minimum LR ratio 0.05, base Muon LR `0.003290470163258143` and base Adam LR `0.0007593392684441868`. Both groups used the same normalized schedule. Re-read these settings rather than inferring LR from the base value or a recent telemetry point. If relative schedules differ in a selected window, derive group-specific coefficients or reject that window for the first implementation.

This is a WSM-inspired surrogate for cooldown. Gradients and optimizer state would evolve differently in a real cooldown; Hero also applies nonlinear norm projections. Sparse saved snapshots further limit fidelity. Evaluate the resulting weights against the latest unaveraged checkpoint.

Restore authoritative FP32 `master_params` when present, otherwise the checkpoint's authoritative parameter tree. Reuse the semantics of `experiments/grug/moe_hero_ep/weights.py::restore_weights`, including checkpoint digest validation and effective pending QB router-bias handling. Average learned parameters in FP32 and cast only for the final consumer. Do not average optimizer states, counters or data-loader state.

Treat QB router biases as routing control state: use the latest checkpoint's effective biases for the first candidate and record this exception to the parameter merge. Do not average raw pending QB updates. Measure routing balance after merging; recalibration is a separate intervention if needed.

Keep the raw convex average as the first candidate. Report norm shrinkage, especially for the norm-preserving MuonH matrices and output head. Norm restoration would change the merge and requires a separate candidate.

Hero has roughly 535B parameters: one FP32 parameter copy is about 2.14 TB. Use distributed or streamed/chunked accumulation. Do not assume the full model fits in host RAM or download checkpoints to a laptop. A whole-model accumulator plus an incoming model already exceeds 4 TB before overhead. Write a new native checkpoint plus a small provenance manifest; do not overwrite any PT checkpoint.

Averaging must run in the same storage region as the source weights. Require all selected source checkpoints, all averaging workers, temporary array storage and the output checkpoint destination to be in that region. For the inspected `s3://marin-us-east-02a/...` root, verify its actual CoreWeave storage region and choose compute there.
