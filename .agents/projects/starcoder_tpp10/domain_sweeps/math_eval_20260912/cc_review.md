## Blockers

**None.** I traced the masking/window arithmetic, padding, aggregation, identity pinning, restore checks, region gating and reuse, and found no defect that would invalidate the numbers or re-open the canceled scope. What I verified:

- **Window arithmetic is correct.** `weights[target - start - 1] = mask[target]` (`evaluate_tpp10_finemath_math.py:75`) is the right off-by-one against `LmExample.causal` + `eval_loss`'s `roll(tokens, -1)`. Since `stride < context` is enforced, `max(previous_end, start+1)` always collapses to `previous_end`, so there is no gap and no duplicate; the closing invariant `Σw == Σmask[1:]` (`:82`) fails closed. Token 0 is the rendered BOS, so `mask[0]=0` and nothing is lost by excluding it.
- **Padding is inert.** `pad_id=eos` but `LmExample.causal` is called without `eos_id`/`segment_ids`, so the mask is plain causal (`lm_model.py:100-113`) — padding sits strictly right of every scored position, with zero weight. Final-batch padding from the loader is `tree_zeros_like` (`loader.py:648`), so its tag row is all-zero and contributes nothing to the per-tag sums.
- **The metric is what the spec says.** `RunningMean.add` is an incremental weighted mean (`stat_utils.py:24`) fed `(batch_loss/batch_weight, batch_weight)`, so `eval/math500/loss = Σwℓ / Σw` — a true ratio of totals over scored solution tokens. `exp()` of that is exactly the documented quantity.
- **Axis identity holds.** `make_example` builds `Axis("position", 2048)`; `Qwen3Config.max_Pos` is `Axis("position", 2048)` (`lm_model.py:168`), so the math sets and the PALOMA cache batch together correctly. `ListAsyncDataset` needs no `finalize()` (`dataset.py:231-238`) — no hang.
- **Control identity resolves uniquely.** `next(... arm == "unmatched")` picks `tpp10_unmatched_p000_s20260910`; the repair plan holds exactly three audits (target p000, unmatched p000, wikipedia matched p050), all seed 20260910. That is the same p=0 anchor `plot_tpp10_domain_sweeps.build_curves` already uses via `controls["matched"]`.
- **Scope is foreclosed structurally.** `validate_spec` rejects any `arm == "target"` endpoint and requires exactly the eight proxy percents (`:199-202`); there is no train loop, one `remote()` call, `original.TPU` is a single v5p-8 pinned to `us-central1-a`, and `require_central1()` gates both `submit` and `evaluate`.

## Should-fix, ranked

1. **The PALOMA restore check destroys its own evidence** (`:263`). `check_close` raises before any receipt is written, so a 6e-5 near-miss on checkpoint five kills the TPU session and leaves no record of the delta or of the math metrics already computed. `repair.audit_checkpoints` deliberately writes the receipt with `"verified": False`, verifies, then rewrites (`repair_tpp10_evaluation.py:366-403`); that two-phase pattern was dropped here. This is the most likely operational failure: PALOMA now shares batches with two datasets it has never shared with, and the 5e-5 tolerance was calibrated against a different companion set.
2. **No collect step.** `--build`/`--submit` only. Eight JSONs land in GCS and nothing enforces the reporting discipline you specified — in particular nothing flags a minimum sitting at p=100 (15.825 epochs, the grid edge). Add `--collect` emitting the curve plus an explicit `boundary_minimum` flag and the second-best gap, so "no >10 claim from a still-improving boundary" is a property of the artifact, not of the prose.
3. **Unverified schema on the two eval objects.** `prepare_math` assumes `row["problem"]`/`row["solution"]` for both (`:108`). MATH-500 uses those names; HF `openai/gsm8k` uses `question`/`answer`, and the repo's other GSM8K pin is `raw/gsm8k/mainhf` (`experiments/datasets/eval.py:404`), not `raw/gsm8k-ef3e8c/`. Fails loudly at build, so it is a "will it start" risk — but confirm before booking the TPU, and while you are there check whether that object preserves GSM8K's `<<48/2=24>>` calculator markup and `#### n` terminator, which would make a nontrivial share of scored tokens pure markup no pretraining corpus contains.
4. **Code pins miss two load-bearing files.** `code_pins()` adds `lm_model.py` but not `data/dataset.py` (ListAsyncDataset/MappedAsyncDataset) or `data/loader.py` — and the zero-padding behaviour at `loader.py:648` is exactly what makes the "padding excluded" claim true. Separately, `code_pins` uses `path.resolve().relative_to(REPO)` while `original.code_pins()` uses unresolved `relative_to`; if REPO is ever reached through a symlink the worker-side `validate_spec` raises spuriously.
5. **`--build` reads regional objects ungated.** `build_spec` downloads both eval objects (twice — once for the sha, again inside `prepare_math`) and tokenizes, with no `require_central1()`. The sibling uncheatable module has the same gap, so it is a pattern rather than a regression, but you asked about region.
6. **Test gap at the prompt boundary.** With the TinyLlama SentencePiece vocabulary, `"Answer: "` ends in a space that BPE merges into the first solution token (`▁The`), and `_assistant_mask_from_generation_spans` marks that token (`tokenizers.py:468`) — matching HF's `return_assistant_tokens_mask`. So the first scored token spans one prompt character. Conventional, and identical across all eight checkpoints, so it cannot bias the p-comparison — but `test_reference_solution_mask_excludes_question_and_padding` asserts `decode(selected).strip() == solution` (`tests/test_tpp10_math_evaluation.py:33`), and that `.strip()` makes the test pass either way. Drop it, assert the convention, and state it in one sentence of the method text.
7. **Control selection is positional.** `next(...)` is unique today but silently seed-ambiguous if a second unmatched audit is ever added; the grid check constrains only `percent`. Assert the run name or `trainer_seed`.

Minor: `model_config(Arm.MATCHED)` is hardcoded while the control is `unmatched` (identical geometry; fail-closed at `load_checkpoint`). `evaluate` re-pins checkpoint metadata but does not re-run `training_evidence` on the worker — adequate given the metadata sha plus the PALOMA restore.

## One common eval plus domain-specific diagnostics

Yes, adopt it. The setup already has that shape; making it explicit helps three ways: the claim shrinks to something falsifiable ("the common eval picks p30 for both; the domain-specific diagnostics disagree" — a statement about evaluation choice, not repetition tolerance); it closes the shopping surface that `analyze_tpp10_domain_eval_optima.py` currently opens by computing minima across all eight metrics and displaying four; and it stops Uncheatable's code weighting from being an unstated confound, because the common eval becomes "one fixed pre-registered selection metric" rather than "the right measure of general quality."

Two conditions. Per-domain diagnostics are not comparable across domains (math PPL and held-out Python BPB are different units), so the pair figure must plot the *common* eval for both domains and put diagnostics in separate panels, never on a shared axis. And each diagnostic must be declared before it is run, or the shopping problem reappears one level down.
