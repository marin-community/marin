### Blocking fixes

**1. Hardware policy is not expressed in code.** `ResourceConfig.preemptible` defaults to **True** (`fray/types.py:438`). Neither `CPU` (`prepare:34`) nor `TPU` (`launch:33`) sets it, so all 28 TPU runs and both prep jobs would schedule preemptible — directly contrary to the stated non-preemptible requirement. Likewise no interactive priority, no `max_retries_preemption`/`max_retries_failure` pinned to 0, and no 48h deadline appear anywhere in the new modules. *Fix:* add `preemptible=False` to both configs and pass the priority/retry/deadline fields explicitly at the `remote(...)` call sites (`prepare:174-177, 192, 212`; `launch:69-74, 251-256`). `with_tpu` forwards `**kwargs` to `ResourceConfig`, so `preemptible=False` is a valid addition. Note `force_run_failed=True` (`launch:273, 293, 300`) re-runs failed steps on re-invocation; that is manual resume, not auto-retry, but state it in the release record.

**2. Evaluation-population parity between the survey and the reused controls is never asserted.** `submit` builds training-time caches from `ASSETS/evaluation.json` (`launch:275`) while `prepare_controls` builds them from `ASSETS/control_evaluation.json` (`launch:238-240`). Only the former is compared to `plan["evaluation_paths"]` (`launch:276`). If the two files' `sources`/`tokenizer_pins` diverge, the 28 new endpoints and the two p=0 controls score different populations — exactly what SPEC:55 forbids, and it would surface only after all training. *Fix:* before submission assert `evaluation.json["sources"] == control_evaluation.json["sources"]` and `evaluation.json["tokenizer_pins"] == control_evaluation.json["tokenizer_pins"]`, and that `prepare_caches` on both returns identical paths for the seven components.

**3. No pre-training check that the seven components become eval sets.** `test:105` asserts they are *absent* from train streams but nothing asserts they are *present* as tagged eval sets. If the tag naming or `tagged_eval_sets` resolution differs from the expected `eval/uncheatable_eval/{name}/bpb` keys in `final_metrics:181`, every run completes and then fails collection — up to 6.66e18 FLOPs per target run. *Fix:* add a config-level assertion (no training) that the materialized `data.tagged_eval_sets(...)` tags cover the seven names plus `experiment.PRIMARY_METRIC`'s PALOMA set.

**4. FineMath parquet memory at 2 CPU / 8 GB.** The byte bound (`prepare:86`, `size_bytes + 32 MiB`) guards re-reads but not resident memory; `iter_batches` materializes a full row group's `text` column before slicing to `batch_size=128`. Objects are 502–512 MB compressed (SPEC:39), so one row group can decompress to several GB. *Fix:* read `parquet.metadata.row_group(i).total_byte_size` from the footer first and fail closed above a budget, or raise the FineMath prep job's RAM. Wikipedia keeps the frozen `4 × quota` compressed bound (`prepare_starcoder_tpp10.py:110` → 363 MiB/shard); that fails closed, but probe it regionally before the batch.
