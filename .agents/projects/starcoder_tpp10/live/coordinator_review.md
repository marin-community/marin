## Verdict

The addition is a sound gate. Nothing lets an unauthorized or unpinned plan reach submission. Three concrete operational defects, then the confirmations.

**1. Wait budget nearly exhausts the coordinator's own task timeout** — `await_starcoder_tpp10_calibration.py:47` waits up to 160 000 s while `submitted_calibration.txt:2` sets `--timeout 172800` (a *per-task* timeout, `client.py:954`). That leaves 3.6 h for eight v5p-8 runs in the worst case. A timeout kill is a failure, and `--max-retries` defaults to 0 (`cli/job.py:904`), so the coordinator would not retry: children die, `collect_results` never runs, and the TPU work is wasted with no metrics. Size the wait so `job_timeout − wait_timeout` covers the whole calibration (e.g. wait ≤ 12 h), or raise `--timeout`.

**2. In-flight training is not reattached across coordinator preemption.** `--max-preemption-retries` defaults to 1000, so a preempted coordinator replays the script from the top. Completed runs *are* reused correctly (`pending_training_steps`, `launch_starcoder_epoch_matching.py:155-171` skips only SUCCESS with a matching recorded fingerprint), but `RemoteCallable.__call__` (`remote.py:70-94`) names each child `verified-training-<uuid4>` and blocks on its handle; the restarted attempt holds no handle and resubmits every non-SUCCESS step as a brand-new job. If an orphaned child survives the restart, two jobs target one output path, arbitrated only by the `.executor_status.lock` lease. Either set `--max-preemption-retries 0` and resume by hand, or give children deterministic names and reattach.

**3. Calibration metrics never leave the pod.** `launch_starcoder_tpp10.py:319` writes `calibration_metrics.csv` (and the plan at :297) into `--output`, the ephemeral bundle workdir; only the plan and release are persisted to GCS. On exit the CSV is lost. Recoverable — re-run `--collect-results` against the archived plan — but the run's endpoint values should be uploaded, not reconstructed.

**Minor.** The audit check at `await:51-54` derives the URI from the digest of the object it compares against, so it can only detect absence, not divergence; its real content is "preparation persisted exactly this audit." A missing object raises a bare `FileNotFoundError` rather than the intended message. And `authorization["preparation_job"]` is trusted verbatim — any succeeded job name satisfies the wait; the substance comes from re-deriving `verify_caches`.

**Confirmed correct.** Gating: the authorization is checked against a freshly rebuilt `plan_sha256`/`design_sha256`, stage, and reviewer (`await:33-40`), `load_design()` re-verifies the frozen design and tokenizer pins, and `training.main --submit` independently re-runs `verify_caches` and `validate_release` (`launch:301-303`). `persist_submission_plan` is create-once and refuses divergent content, so a restart cannot silently rewrite the release. Failed preparation: `raise_on_failure=True` propagates `JobFailedError` before any submission, and a job marked complete by hand still fails `verify_caches` ("Data preparation is incomplete"). Placement: submit pins `--region/--zone`, `require_central1()` checks instance zone plus `MARIN_PREFIX` before the wait and again before submit, and children inherit the reviewed TPU `regions/zone` and prefix env. No later stage is released — the stage is hard-coded, `--collect-results` is unused, and no canary/pilot/dense path is reachable.
