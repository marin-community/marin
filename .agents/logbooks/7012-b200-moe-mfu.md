# B200 MoE MFU: Task Logbook

Experiment ID prefix: `B200MFU-###`. All runs on a shared 8×B200-per-node cluster
(single node unless noted); "same-node pair" means both arms pinned to one node,
run sequentially. Driver: `grug_moe_row13.py` on branch
[`mcwitt/sonic-cute-wgrad`](https://github.com/marin-community/marin/tree/mcwitt/sonic-cute-wgrad)
(off `sonic-cute-moe-b200`). Row-13 config (#6979): d2560 / 26L / 64 experts top-4 /
MHA / EP1+FSDP / MuonH / stacked-scan / b128 / seq4k / `gpu_fa4_cute` attention.
Steady-state median MFU vs B200 bf16 peak (2.25e15 FLOP/s/GPU), 20 steps, warmup 8.

## Scope
- Goal: raise single-node B200 MFU toward the ≥20 %-on-a-rack target of #7012; identify which levers actually move step time.
- Primary metric: `steady_median_mfu_b200` from the row-13 driver (tokens/s as secondary).
- Constraints: shared cluster etiquette (≤2 nodes at a time); no cluster identifiers in durable output.
- Coordinating issue: https://github.com/marin-community/marin/issues/7012

## Current TL;DR
EP news (B200MFU-017): **`ring` is the only viable EP backend on B200 today** —
13.3/13.4/12.9 % at EP2/4/8 (~-1.8 pp vs the 15.14 % sonic_cute EP1 control),
while `ragged_all_to_all` is catastrophic (0.97 % / 51 s per step at EP2, step
time ∝ 1/EP; dispatch machinery, not GEMM — Triton ragged_dot microbenches at
397–859 TF/s, only ~2.5–3.7× off QuACK). EP backends can't use the QuACK
`sonic_cute` GEMM (local-only backend).
d2560 best is now **15.67 %** (B200MFU-015): `remat_mode=all_but_moe` + slim
sonic_cute custom_vjp residuals (+0.51 pp over the same-node control), on top of a
real +0.14 pp from the 256×256 tiles once the stale-import bug (B200MFU-014) was
fixed. Naive remat splits OOM — custom_vjp residuals and fp32 norm saves stack ×26
in the scan (B200MFU-013) — the working recipe is: slim what the vjp saves, then
checkpoint everything except the MoE. Profile context (B200MFU-007): attention
30.3 %, remat recompute ~25 %, MoE GEMMs 24 %, optimizer 4.4 %, NCCL ~10 %.
Native XLA `ragged_dot` has no working fast path on any tested stack (cuDNN
enumerates zero plans on SM100, B200MFU-009/-010). TE `grouped_dense` is
QuACK-class (1,449 TF/s, B200MFU-011): the MXFP8 + rack-EP vehicle.

## Current baseline
d2560: **15.67 %** best (`all_but_moe` remat + slim vjp + tiles, B200MFU-015);
recompute_all control on the same stack: 15.16 %. Historical: 15.01–15.02 %
(sonic_cute + quack wgrad, no tiles — see B200MFU-014).
d5120: **17.88 %** (wgrad stack, B200MFU-006; `all_but_moe` won't fit at d5120 —
recompute_all already peaks at 157 GiB there). Controls match #7012 table (14.9 / 17.8).

## Hypothesis Queue

### Active
- `H-mxfp8`: MXFP8 on QuACK seam (or via TE `grouped_dense`); ceiling ~1.1× e2e for MoE-only (24 % share) — larger if attention/dense included.
- `H-fa4lse`: expose FA4's `lse` as a primal output so (o, lse) become name-saveable → whole-block checkpoint that skips the FA4 fwd re-run (~6.7 % of kernel time, est. +~1 pp) at ~+9 GiB. Requires a custom_vjp signature change in `_fa4_cute.py`. Memory check needed on top of all_but_moe's 152 GiB peak.
- `H-attnbwd`: FA4 bwd at 13.8 ms vs fwd 5.9 ms (~2.3× FLOPs → roughly fair); check kernel efficiency headroom before acting.
- `H-a2a-nccl`: the a2a backend's 297 ms/call is the *default one-shot kernel path*, not the only one — `--xla_gpu_unsupported_use_ragged_all_to_all_one_shot_kernel=false` switches the same thunk to NCCL send/recv with true ragged sizes (near-peak wire utilization per openxla/xla#33386), at the cost of a host sync + index a2a per call. One-flag same-node ladder vs ring (B200MFU-023).

### Blocked
- `H-te`: TransformerEngine as the MXFP8 + rack-EP vehicle (grouped GEMM proven QuACK-class, B200MFU-011; `fp8_autocast`/quantize APIs present; NCCL_EP per TE PR #3036). Blocker: remat surgery first (bigger single-node win). Resume when: MXFP8 phase starts. Source-read of TE PRs #3034/#3036 + the WIP JAX MoE branch (2026-07-15): the "8192-token" limit is a *staging-buffer sizing default* (`max_tokens_per_rank` at `ep_bootstrap`), not kernel-structural; comm SM budget is a one-integer `max_num_sms` knob (default auto) and TE never grid-sizes the GEMM to the remainder (one-sided specialization); dispatch wire is bf16-only — fp8/MXFP8 happens post-dispatch via `grouped_quantize` right before `grouped_gemm`; dispatch/combine run in global mesh view with only the FFN inside `shard_map`; requires process-per-GPU (`local_device_count()==1`) and disables NCCL comm-splitting + command-buffer capture around the EP FFI ops. API probe (2026-07-15, job on the container stack): TE 2.15.0+42b840051 does **not** ship the NCCL_EP JAX surface — no `jax.moe`/`jax.ep` modules, no nccl/bootstrap/dispatch symbols in the pybind ext (it does have `grouped_dense`, `permutation`, `router`) — so an NCCL_EP microbench vs the 297 ms/call XLA figure (B200MFU-018) first requires building TE from the WIP PR branch.

### Falsified / Dead End
- `H-smspec`: SM specialization (comm/compute SM partitioning, as in DeepEP's dedicated-SM budget and TE NCCL_EP's `max_num_sms`) helps at single node. **Falsified for EP1+FSDP** (B200MFU-016): pinning NCCL CTAs loses monotonically (auto/32ch 15.61 → pin16 15.41 → pin8 14.61 %); sizing QuACK persistent grids to the 132-SM remainder (`SONIC_CUTE_SM_CARVEOUT=16`, commit 2949be3bb) costs −0.07 pp alone and does not recover the pin's loss when combined (15.43 %). NCCL's autotuned channel count is already right here. **Also falsified in the EP regime** (B200MFU-021, single-node ring EP8): control 12.97 → pin16 11.75 → pin8 9.78 % — same monotone shape, ~6× larger losses. On this stack the carve-out is a bandwidth cap; the valuable half of the advice is the chunked-pipeline decomposition (→ TE NCCL_EP, H-te), not the SM budget.
- `H-wgrad`: QuACK varlen-k wgrad ≫ XLA wgrad e2e. Falsified: +0.06–0.08 pp only (B200MFU-003/-004). Kernel is bit-exact and kept (completeness + MXFP8 substrate).
- `H-tiles`: per-site tile autotune lifts e2e. LANDED small: real e2e effect is +0.14 pp (15.02 → 15.16, B200MFU-015) once the stale-import bug (B200MFU-014) was fixed; the earlier "null" verdict was an artifact. Microbench ×1.08–1.28. Default-on.
- `H-remat`: reclaim the ~25 % remat recompute tax via block-split checkpointing. LANDED as `all_but_moe` + slim vjp residuals: **+0.51 pp** (15.16 → 15.67, B200MFU-015). Naive attn_only/moe_only splits OOM (B200MFU-013); the +2–3 pp estimate was too optimistic — the skippable piece that fits in memory is the MoE fwd (~3.3 % of step), not the whole re-run. Remaining remat upside → H-fa4lse.
- `H-comms`: EP1+FSDP collectives dominate. Falsified: NCCL ~10 % of step (B200MFU-007).
- `H-ns`: batching MuonH Newton-Schulz is a big win. Falsified: NS total = 0.60 pp (B200MFU-008a); already batched via `_newtonschulz_4d_distributed`.
- `H-savemoe`: `remat_mode=save_moe` skips MoE recompute. Falsified for sonic_cute: +65 GiB, 0 gain — `_expert_mlp` is a custom_vjp whose residuals can't be name-saved through `jax.checkpoint` (B200MFU-008b).
- `H-ngc`: NGC 26.05 makes native `ragged_dot` competitive. Falsified: default path = same dense-materialized cuBLAS lowering (~26 TF/s eff.); `use_ragged_dot_fusion` flag absent from their runtime; `use_ragged_dot_grouped_gemm` parses but is the ROCm/hipBLASLt path (upstream default-true, no-op on CUDA) (B200MFU-010).
- `H-flags`: ragged-dot-fusion / LHS flags help on stock jax. Falsified e2e and explained: sonic backend never emits `ragged_dot` HLO; when forced, fusion fires then autotuning fails "No supported configs" (B200MFU-009). LHS likely already default.
- `H-pgle`: PGLE closes part of the ~9 % idle share. Falsified at single node: +0.06 pp over control on a 3-arm same-node ladder (B200MFU-012). Revisit at rack scale where inter-node collectives give the scheduler something to hide.

## Decision log
- 2026-07-13: adopt QuACK wgrad + 256×256 tiles as default on the branch (harmless, marginally positive) — B200MFU-003..006.
- 2026-07-14: prioritize NVIDIA-stack probes (ragged-dot fusion per the NGC JAX 26.05 release notes, LHS, NGC container) ahead of remat/MXFP8; container first.
- 2026-07-14: remat surgery ranked highest-EV code change; MXFP8 after, with quantified ceiling.
- 2026-07-15: adopt `remat_mode=all_but_moe` + slim sonic_cute residuals as the d2560 default (B200MFU-015); keep `recompute_all` for d5120 (memory). Next: MXFP8 via TE, with H-fa4lse as a cheaper parallel candidate.
- 2026-07-15: EP on B200 goes through `ring` (13.3 % at EP2, B200MFU-017); `ragged_all_to_all` is blocked upstream (XLA GPU lowering, B200MFU-018) — don't spend more tuning on it. Next EP probe: TE NCCL_EP dispatch/combine microbench vs the 297 ms/call XLA number.
- 2026-07-16: "a2a is blocked upstream" softened — source read at our XLA pin (B200MFU-023) shows the 297 ms/call path is the default one-shot kernel, with an NCCL ragged path one flag away; H-a2a-nccl queued before writing a2a off permanently. The "GPU lowers to dense comms" claim is falsified for all released jaxlibs ≥ 0.5.0.

### 2026-07-14 — B200MFU-010: NGC JAX 26.05 container — native ragged_dot verdict
- Setup: apptainer SIF (jax 0.10.0.dev+c98e1bb97 / NVIDIA jaxlib dev20260714, TE 2.15, baked-in `--xla_gpu_enable_latency_hiding_scheduler=true`); env via PYTHONPATH overlay (in-tree `lib/*/src`, site-packages minus ABI-coupled dirs, CPU-only torch for flash_attn's host import; `sonic_cute` import made optional, commit `767712e59`).
- Result: 1-GPU driver mini-train blocked — sonic/scatter grouped GEMMs are Pallas-triton kernels and hit an MLIR bytecode-version mismatch in-container. Microbench (`ragged_fusion_probe.py`): default = same dense-materialized `[262144,163840]` cuBLAS lowering as upstream, 25.9–26.1 TF/s effective (first attempt failed autotuning until `XLA_PYTHON_CLIENT_MEM_FRACTION=0.95` — the dense path materializes an ~86 GB intermediate). `--xla_gpu_experimental_use_ragged_dot_fusion`: **unknown flag** in their runtime. `--xla_gpu_experimental_use_ragged_dot_grouped_gemm`: parses, changes nothing — upstream source says it's the ROCm/hipBLASLt lowering.
- Cross-check on upstream **jax 0.10.2** (shadow-dir install): fusion fails identically — "No supported configs found"; cuDNN frontend logs show zero plan candidates. Per current XLA source (`backends/gpu/autotuner/cudnn.cc`), ragged-dot fusions are delegated to cuDNN unconditionally, so the empty config list comes from cuDNN plan enumeration: a **cuDNN capability gap on SM100** for this graph pattern, not an XLA arch gate, and not fixed by a jax upgrade.
- Interpretation: no native-XLA fast path for ragged_dot exists on any stack we can obtain today. `exploratory→replicated` across three stacks.

### 2026-07-14 — B200MFU-013: attention-only remat — OOM, root-caused
- Implementation: `remat_mode="attn_only"` (commit `2c8f3fe2b` / cluster `428a563`): `eqx.filter_checkpoint` around only the attention sub-block (norms + gated-norm + lax.cond'd FA4), MoE left live; masks/Bool scan-input passed as explicit checkpoint args. Also fixed `remat_mode="none"` silently behaving as `recompute_all`. CPU smoke (8 fake devices, tiny model): all modes bit-identical loss/grad-norm on loop and scan paths.
- Result: job 3236 OOM at first step — **temp arena 283.63 GiB vs 36.89 GiB for recompute_all** (compile-only AOT probe, `remat_oom_probe.py`, jobs 3264/3265). Largest stacked-over-scan buffers: 3×`bf16[26,262144,2560]` = 97.5 GiB (sonic_cute custom_vjp residuals: sorted dispatch input, `gu`, +1) · 3×`f32[26,16,4096,2560]` = 48.8 GiB (residual stream/norm saves upcast to fp32 by the mp policy) · `bf16[26,64,2560,2560]`+`bf16[26,64,1280,2560]` = 30.5 GiB (**all-gathered FSDP expert weights pinned per layer** instead of re-gathered in bwd) · `h` 16.3 GiB · misc ~16 GiB.
- Interpretation: attn_only is structurally infeasible at d2560/26L on 192 GB: the custom_vjp pins its residuals (incl. gathered weights) and the homogeneous scan stacks all 26 layers; no save-policy can trim custom_vjp residuals (cf. B200MFU-008b).
- Follow-up `moe_only` (inverse split): **also OOM** — temp 247.70 GiB (probe 3268, e2e 3269). With attention live, autodiff saves the attention-side intermediates **in fp32** (norm/rope internals: multiple `f32[26,16,4096,2560]` + `f32[26,16,4096,20,128]` stacks). Both naive splits falsified.
- v2 design (in flight): (a) **slim the sonic_cute custom_vjp residuals** — we own the vjp, so backward re-gathers `x_dispatch` from `(x, token_dispatch)` hint args, recomputes `h = swiglu(gu)` elementwise, and stores `w13`/`w2` FSDP-sharded via `reshard` (re-gathered in bwd — the same all-gather whole-block remat pays); (b) **`all_but_moe` mode** — checkpoint attention *and* all norms (kills the fp32 saves), leaving only router → dispatch → expert GEMMs → combine + shared expert live. Projected temp ≈ 120–150 GiB; reclaims the MoE-forward share (~8 %) of the remat tax → est. +1–1.5 pp. Commits `01b8e7c92` (local) / `8e56ff9` (cluster); full-bwd parity test `test_sonic_slim_parity.py` added.

### 2026-07-15 — B200MFU-015: all_but_moe remat + slim vjp — **+0.51 pp; d2560 best 15.67 %**

Gathered-weight stacks now sharded (`bf16[26,64,320,2560]` = 2.54 GiB), `h` and `x_dispatch` gone; remaining big items are the irreducible pins: `gu` + `out_dispatch` (2 × 32.5 GiB), bf16 hidden/mlp_in (8.1 + 8.1).

### 2026-07-16 — B200MFU-023: background research — the "ragged_all_to_all is dense on GPU" claim (source-verified at our XLA pin)
- Effort: medium. Stop rule: stop once GPU lowering paths + defaults are verified at our exact pin and the TPU side is graded; no new sources were changing the verdict. Question: does `jax.lax.ragged_all_to_all` lower to *dense* comms on GPU but true ragged comms on TPU?
- Method: read XLA sources at commit `9b635916ecc` — the pin of our jaxlib 0.10.1 (`jax-ml/jax` tag `jax-v0.10.1` → `third_party/xla/revision.bzl`) — plus flag-default archaeology across the XLA pins of jax v0.4.38/0.5.0/0.5.3/0.6.2/0.7.0/0.8.0/0.9.0.
- **Verdict: the claim is false for wire traffic on every released jaxlib ≥ 0.5.0, including ours.** A dense lowering *does exist* — [`RaggedAllToAllDecomposer`](https://github.com/openxla/xla/blob/9b635916ecc6df6efee62d8e4b0c7ef87ef84d69/xla/backends/gpu/transforms/ragged_all_to_all_decomposer.h) pads every ragged row to a dense `all-to-all` + `dynamic-update-slice`, self-described as "a temporary solution to unblock end-to-end integration … on GPU" — but it is gated behind `xla_gpu_unsupported_enable_ragged_all_to_all_decomposer`, which has defaulted to **false at every pin checked back to jax v0.4.38** (Dec 2024, when the op landed). At the v0.4.38 pin there was *no* GPU thunk at all (the op just didn't run without the flag), which is the likely origin of the claim; from jaxlib 0.5.0 a native NCCL thunk exists.
- What GPU actually does at our pin ([`ragged_all_to_all_thunk.cc`](https://github.com/openxla/xla/blob/9b635916ecc6df6efee62d8e4b0c7ef87ef84d69/xla/backends/gpu/runtime/ragged_all_to_all_thunk.cc), `RunCollective`), three runtime paths in priority order:
  1. **One-shot kernel + NCCL symmetric memory** (NVLink/LSA domain, NCCL ≥ 2.28): XLA's own `RaggedAllToAllKernelImpl` P2P-writes rows into peer buffers, flanked by `MultiGpuBarrierKernelImpl` barriers. Ragged (reads `send_sizes` on device, copies only real rows) — this is exactly the 297 ms/call + barriers path we profiled in B200MFU-018. Default **on** (`xla_gpu_unsupported_use_ragged_all_to_all_one_shot_kernel=true` since ~jaxlib 0.5.3); zero-copy variant default off, so it also eats an extra D2D copy of the output buffer.
  2. Same one-shot kernel via CUDA peer access when symmetric memory is unavailable but all ranks are on one host.
  3. **NCCL fallback** (multi-host, or one-shot disabled/unsupported): grouped `ncclSend`/`ncclRecv` per (peer, update) with **true ragged sizes** on the wire — but each call first does an extra all-to-all on the output-offsets index buffer *and* a D2H copy of all four metadata tensors with `BlockHostUntilDone()`, i.e. a host sync inside every dispatch/combine. Ragged on the wire, expensive on dispatch.
- External corroboration: [openxla/xla#33386](https://github.com/openxla/xla/issues/33386) (2025-10-30, unanswered) measures exactly this split on 8×B200: **~2 % of NVLink** bandwidth single-host (one-shot kernel path) vs **~100 % of the cross-node wire** at 2 nodes (NCCL fallback path). Independently confirms both our B200MFU-018 pathology and that the multi-host path is bandwidth-efficient (its cost is the per-call host sync, not padding).
- TPU side: not publicly inspectable (closed compiler), so "true ragged comms on TPU" can't be source-verified; graded plausible-and-uncontradicted — the op was built for TPU MoE, MaxText uses it for production EP dispatch/combine (`src/maxtext/layers/moe.py`), and per-backend thunk support is the model (XLA:CPU raises `UNIMPLEMENTED` rather than falling back to anything dense, [jax#34755](https://github.com/jax-ml/jax/issues/34755)).
- Refinement of B200MFU-018's interpretation: "XLA lowers it to a peer-copy kernel instead of NCCL" is right about the *default* path but incomplete — an NCCL path exists in the same thunk, one flag away (`--xla_gpu_unsupported_use_ragged_all_to_all_one_shot_kernel=false`), no rebuild needed. Given #33386's near-peak NCCL wire numbers, that flag could plausibly collapse the 297 ms/call by orders of magnitude even single-node (NCCL send/recv over NVLink), at the price of a host sync + index a2a per call → new hypothesis `H-a2a-nccl`. Also relevant to any future 2-node a2a attempt: multi-host always takes the NCCL fallback (one-shot requires a single NVLink domain), and `RaggedAllToAllMultiHostDecomposer` (splits intra/inter-host) is default-off.
- Recommended next experiment (cheap, single flag): same-node pair, d2560 row-13 EP8, `MOE=ragged_all_to_all`, control vs `XLA_FLAGS=--xla_gpu_unsupported_use_ragged_all_to_all_one_shot_kernel=false`. Expected signal: a2a step time drops from ~51 s toward ring's ~3.7 s if NCCL wire dominates; falsifier: host-sync/dispatch overhead keeps it ≫ ring, in which case a2a stays dead and TE NCCL_EP remains the vehicle. Secondary arm if promising: `--xla_gpu_experimental_ragged_all_to_all_zero_copy=true` (kills the double copy on the one-shot path).
- Source ledger: XLA sources pinned at `9b635916ecc` (thunk, decomposer, kernel lib, `debug_options_flags.cc`, `gpu_compiler.cc`) — external code, high confidence; jax↔XLA pin mapping via jax repo tags — high; xla#33386 — GitHub issue, single reporter but methodology shown, medium-high; MaxText moe.py — external code, high for "TPU production use", indirect for "ragged on the TPU wire"; TPU compiler behavior — unverifiable publicly, medium.
