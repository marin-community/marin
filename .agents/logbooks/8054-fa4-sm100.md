# Native SM100 FA4 on the FSDP Grug hero

## Scope

Determine whether the FSDP Grug hero runs a native SM100 FA4 kernel on GB200, make the native path
correct for packed local/global attention, and measure it against the current path at approximately
1B active parameters. This is a disposable throughput experiment: 20 steps, no checkpoints, four
16-GPU arms, and 30-day temporary outputs.

## Current TL;DR

The production `gpu_fa4_cute` path does not run the upstream SM100 kernel. Its forward kernel is the
Grug-specific `SegmentedFlashAttentionForwardAmpere`; on compute capability 10.x its backward path
selects the local SM120 fork. Both are forced to 64x64 tiles and 128 threads at head dimension 128.

The repository already has a separate `gpu_fa4_thd` backend that dispatches compute capability
10.x/11.x to upstream `FlashAttentionForwardSm100` and `FlashAttentionBackwardSm100`, with 128x128
tiles and the SM100 backward two-CTA configuration. The missing work is not an external build flag.
The FSDP hero rebuilds its masks without the dataset's fixed-shape THD segment metadata, and its
scanned local/global selection is encoded only as bounds for the custom segmented kernel. The
experiment adapter preserves the THD metadata and selects native local/full-causal kernels under the
existing per-layer predicate.

## Current baseline

- Source: `25b0196588b2254b50a9ef5d9d23a7657193722c` before the experiment adapter.
- Hardware per arm: 4 GB200 nodes, 4 GPUs per node, 16 GPUs total.
- Model: 15.44B total parameters, 869,793,792 active parameters; width 2048, 18 layers, 128 experts,
  top-4 routing, two shared experts, sequence length 4096, batch size 512.
- Attention mix: 15 sliding-window layers at window 512 and 3 full-causal layers; head dimension 128.
- Score: median `throughput/duration` over steps 5-19. Profiled arms exclude capture steps 10-12
  from throughput scoring.
- Controls: one unprofiled and one profiled arm per backend, launched in the same allocation window.

## Hypothesis queue

1. Native SM100 THD compiles and preserves packed-document, sliding-window, and full-causal
   semantics in the scanned hero model.
2. Native SM100 lowers attention time enough to improve whole-step median duration beyond the
   concurrent control spread.
3. If whole-step movement is small, XPlane still shows whether the native kernel reduces attention
   work and whether another stage hides the gain.

## Background research brief

Effort: medium. The question is narrow, but an apparently simple backend flip crosses packed-data
metadata, JAX scan static fields, and local/global attention semantics.

Current Marin evidence:

- `experiments/grug/moe_hero_fsdp/heuristic.py` selects `gpu_fa4_cute` for the hero.
- `_fa4_cute.py` documents that the segmented port is not the native SM100 implementation and
  forces the 64x64/128-thread configuration on compute capability 10.x.
- `_fa4_thd.py` dispatches compute capability 10.x/11.x to upstream SM100 forward/backward classes.
- Issue #7483 records direct GB200 value/gradient parity for THD full-causal and sliding attention
  after the fixes in PR #7630.
- Issue #8053 identifies native SM100 FA4 as a ranked hero optimization; issue #8054 defines the
  matched-control, 20-step scoring protocol used here.

External prior:

- Marin pins `flash-attn-4==4.0.0b16`, upstream commit
  `b02b07e1a10238fe12831b80a8937ed59b1353a5`.
- That upstream release's `flash_fwd_sm100.py` and `flash_bwd_sm100.py` use SM100 `tcgen05`
  implementations. Its interface selects those classes on compute capability 10.x/11.x.

Negative leads:

- There is no missing SM100 build/config flag in the production custom backend. It is a different
  kernel family, not upstream dispatch accidentally disabled.
- Replacing only `attention_implementation` is not correct: it loses THD segment metadata before
  attention and would encode the dynamic layer window incorrectly.
- The previous THD correctness failure is not current evidence against the experiment; issue #7483
  was closed after direct GB200 forward/backward parity passed.

Recommended experiment: run matched `gpu_fa4_cute` and `gpu_fa4_thd` arms from one clean pinned
commit, with one XPlane capture per backend and concurrent unprofiled throughput replicas.

## Decision log

- Use the existing THD backend rather than porting the segmented kernel to SM100 before measuring.
- Preserve production `gpu_fa4_cute` behavior and branch only when the configured backend is
  `gpu_fa4_thd`.
- Use 16 GPUs per arm so four concurrent arms occupy one 64-GPU rack while retaining rack-local FSDP.
- Disable optimizer offload, checkpoints, and watch dumps for this bounded performance diagnostic.

## Negative results index

- Runs w1-w9 produced no THD measurement. Every `gpu_fa4_thd` arm died before the training loop, so
  none recorded a single `throughput/duration` step in W&B. The native SM100 path was never
  exercised on GB200 by those attempts; their failures carry no evidence about the kernel itself.
- `_fa4_cute.py` already records a prior comparison against upstream dense 128x128 on B200 d5120
  Grug shapes, where the segmented 64x64 configuration was faster. That is prior evidence against a
  large native-SM100 win, though it compared tile configuration rather than the packed THD path.

### 2026-08-08T00:55:00Z — coordinator-port fix unmasks the real THD failure

Rebased onto `98af0b6979` ([iris] Select the JAX coordinator port on global rank 0, #7994), which
replaces the fixed port 8476 with a rank-0 `find_free_port()` selection. Runs w1-w9 had been failing
in JAX coordination, and those failures were masking the actual behavior of the native path.

With the fix live (`initialize_jax bootstrap inputs: ... requested_port=None` confirms it shipped),
w10 launched four matched arms. Both `gpu_fa4_cute` arms succeeded. Both `gpu_fa4_thd` arms failed
immediately and identically:

    NotImplementedError: gpu_fa4_thd_attention requires fixed-shape THD segment metadata under JAX.

Root cause: `AttentionMask.thd_segment_metadata` is populated only by `with_segment_ids(...,
max_segments=...)`. The grug conversion `grug_attention_mask_from_named`
(`lib/levanter/src/levanter/data/text/examples.py:320`) constructs the mask without `max_segments`,
so the metadata is `None` on every grug path. The adapter preserved that `None` faithfully, so
preserving it was a no-op; the metadata has to be derived, not forwarded.

Cute baseline, median `throughput/duration` over steps 5-19:

| arm | median s/step |
| --- | --- |
| w1-cute-a | 2.5574 |
| w10-cute-a | 2.5615 |
| w10-cute-profile | 2.5705 |

Three independent arms span 0.5%, which sets the control noise floor for scoring any native gain.

### 2026-08-08T01:14:00Z — two more native-path failures, both real

Fixing the metadata moved the native arm past its first error into two further genuine failures,
each caught only on GB200:

1. Deriving the metadata straight from the batch-sharded segment ids aborts with
   `Resource axis: replica_dcn of P(('replica_dcn', 'data', 'expert'), None) is not found in
   mesh: ()`. `thd_segment_metadata_from_segment_ids` vmaps a per-row scan, and the inner
   `concatenate` cannot carry a batch-sharded row spec because the abstract mesh is empty under
   vmap. Fixed by replicating the ids first, which the kernel already does for its global prefix
   sum. This reproduces on eight CPU devices with the hero's four-axis mesh, so it is now a local
   test rather than a 16-GPU failure.

### 2026-08-08T01:10:00Z — why the two kernels are not interchangeable

The hero does not pack documents. `_effective_pack` is false for the text format, so the data path is
a plain `CausalLmDataset` over fixed 4096-token windows, and segment ids come from an EOS cumsum in
`GrugLmExample.causal` (`lib/levanter/src/levanter/data/text/examples.py:165`). No `max_segments` is
passed anywhere on that path, so no config bounds the number of documents in a window; it is whatever
the corpus puts there.

That is the structural reason the swap is not a flag:

- The native SM100 THD kernel is varlen. It needs `cu_seqlens` at a static shape, so it needs a
  static upper bound on documents per sequence.
- The hero's document count per sequence is data-dependent and unbounded.
- The custom segmented kernel sidesteps this by encoding document boundaries as per-token lower
  bounds, which is shape-static regardless of how many documents a window holds.

So the segmented fork is not an accident of history that forgot to enable SM100; it is what makes
unbounded packed-document attention expressible under JIT. Running native SM100 here requires
choosing a static `max_segments` and padding to it, which the segmented path never has to do.

The adapter now derives the metadata (`_thd_base_mask`) instead of forwarding the `None` the
conversion always produces. Derivation cost is independent of `max_segments` (the underlying
`jnp.nonzero` sorts over `seq_len`), but `max_segments` sets the `cu_seqlens` length to
`batch * max_segments + 1` and is replicated for a global prefix sum, so the bound is a real
performance parameter and not a free safety margin.
