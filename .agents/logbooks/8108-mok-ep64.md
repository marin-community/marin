# MoK EP64: Task Logbook

## Current TL;DR

The upstream kernel explicitly supports EP64, while Marin's adapter is fixed to process-local EP4.
The first treatment uses 64 supervised one-GPU JAX processes and PyTorch symmetric memory only as
the remote workspace mapper. A standalone JAX+Torch probe must pass before the fused kernel changes.
Native CUDA fabric VMM is the fallback if the PyTorch backend cannot expose all 64 peers.

## Scope

- Goal: Run MoK forward/backward training across one 64-GB200 NVLink domain.
- Primary metrics: numerical parity, exact drop accounting, bounded failure closure, stable 25/100
  step training, tokens/s, MFU, HBM, and host-memory headroom.
- Constraints: one hard NVLink domain, no task retries, runtime-staged inputs first, no claim of
  strict droplessness below factor 64.
- Coordinating issue: https://github.com/marin-community/marin/issues/8108

## Baseline

- Stable local EP4 snapshot: `bceba3c7814f45f556109f202386f85c12844527`.
- Sealed v15 scale: one-rack 25-step 309,026.654 TPS and two-rack 100-step 553,963.070 TPS, both
  data-parallel compositions of EP4 rather than EP64.
- Existing EP64 fixed-all-to-all hero: about 309k TPS at the production rack shape; a fresh matched
  control is required for final comparison.

## Hypothesis Queue

### Active

- `MOK-EP64-H1`: PyTorch 2.11 symmetric memory exposes all ranks in one NVL72 while coexisting with
  one-GPU JAX processes. Next: EP8 then EP64 standalone probe.
- `MOK-EP64-H2`: Upstream's EP64 BF16 instantiation works with Marin's staged workspace and JAX
  schedule. Next: small forward/VJP parity after H1.
- `MOK-EP64-H3`: Full-expert cancellation and status agreement close synchronous failures without
  a hang. Next: rank-0/rank-63 matrix after H2.

### Blocked

- `MOK-EP64-H4`: Cross-process XLA zero-copy. Blocked on a correct symmetric staged implementation.

### Falsified / Dead End

- JAX/NCCL direct one-sided EP64 transport on the current stack: rank-32 metadata-only failures are
  recorded in https://echo.oa.dev/wiki/94 and the MoonEP logbook.

## 2026-08-13 11:40 PDT — Probe misuses the active PyTorch CUDA backend

- Command: identity `/dlwh/mok-ep8-symm-mem-004-20260813-1140-coord` at pushed commit
  `0e02961222d1e1ed94b9c04482964b1030badd88`; the probe resolved each pod's Gloo interface from its
  Iris-advertised address.
- Result: all eight ranks initialized one-GPU JAX, passed IMEX and NVLink-fabric validation, formed
  the cross-pod Gloo metadata group, and gathered uniform fabric metadata. Every rank then failed
  at `torch.distributed._symmetric_memory.set_backend("CUDA")` with
  `SymmetricMemory does not find allocation backend CUDA`. No arena was allocated and no transport
  result was emitted.
- Terminal: both four-GPU tasks and the coordinator failed with retries/preemptions 0. Evidence is
  `scratch/20260813-1140_ep8_symm_mem_monitoring_state.json`.
- Diagnosis: the probe misused the PyTorch 2.11 API. Its CUDA translation unit registers CUDA either
  as the active allocator or as an available alternative. `set_backend("CUDA")` checks only the
  alternative map, so it raises this exact error when CUDA is already active. Official tests query
  `get_backend(device)` and allocate without setting it.
- Next action: assert the active backend is CUDA, allocate directly, and repeat EP8. Native CUDA
  fabric VMM remains the fallback only if the allocator or rendezvous itself fails.

## 2026-08-13 11:56 PDT — First EP64 gate exposes probe phase skew

- Command: `/dlwh/mok-ep64-symm-mem-001-20260813-1156-coord` at pushed commit
  `b52a619b0d55ff7248bdd1d6673d4ce28c72d974`; 16 tasks × four GB200, 64 one-GPU processes,
  4,096-byte arenas, three generations, and all retry/failure/preemption limits 0.
- Result: all 64 ranks initialized JAX, passed fabric preflight, formed the Gloo metadata group, and
  created the CUDA symmetric arenas. During the first generation, the device barrier timed out
  waiting for scattered ranks including 12, 14, 15, 32, and 35. The timeout traps the CUDA context,
  so no accepted JSON was emitted and the gang failed terminally.
- Diagnosis: the barrier API names its parameter `timeout_ms` and implements milliseconds, although
  its fatal message incorrectly prints "microseconds." The full 180-second timeout was consumed.
  Before the next device barrier, every rank performs hundreds of scalar `.item()` remote reads in
  Python; EP64 host scheduling skew can therefore exceed the device wait even though mappings are
  valid. This gate does not isolate rank 32 because the missing set is scattered.
- Next action: add a bounded Gloo phase barrier and CUDA synchronization before every device-side
  fabric barrier. This is probe-only alignment; production MoK publishes readiness from fused
  device code and adds no host barrier. Repeat a new EP64 identity with retries 0.

### Correction after full fatal aggregation

The timeout was not random cold-arrival evidence. Exactly 59 receiver ranks each reported the same
five missing sources `{12, 14, 15, 32, 35}` on channel 1; those five ranks emitted no receive
timeout. All other ranks had passed channel 0, completed remote reads, and issued writes. The five
sources therefore either stalled during their scalar peer-access loops or could not publish through
their signal pads. The phase-aligned rerun remains useful because its Gloo barrier distinguishes
those cases, but the scheduling-skew diagnosis above is retracted until that discriminator runs.

- Command: coordinator `/dlwh/mok-ep64-native-004-2l2s-20260813-1945-coord` at pushed commit

  one atomic rename. Keep the native build's existing digest lock for the subsequent shared compile.
