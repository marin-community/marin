3These lldb scripts read NCCL's proxy-op pool state from a wedged rank and distinguish the
4proxy-slot-leak deadlock (root cause of #7344 on NCCL 2.28.9 / aarch64) from any other stall
5with the same surface signature. Total time on a live wedge: ~15 minutes.
6 
7The scripts were written against a specific wedge and carry hardcoded addresses. They are
8kept as executable documentation of the method; edit the constants at the top for a new
9wedge. The workflow that produced them, in order:
10 
111. **Find the lagging rank** — NCCL RAS from any task:
12   `echo verbose status | nc localhost 28028`, look for the `MISMATCH` warning naming the
13   rank and node IP. Map node IP → pod with `kubectl -n iris get pods -o wide`
14   (`KUBECONFIG=~/.kube/coreweave-iris`). The trainer is PID 1 in the `task` container;
15   `/usr/bin/lldb` is in the image.
162. **Dump all thread stacks** —
17   `lldb -p 1 --batch -o "thread backtrace all" -o detach -o quit > /tmp/btall.txt`.
18   In a slot-leak wedge you find: one thread spinning in `ncclLocalOpAppend`
19   (proxy.cc:499), its comm's own progress thread in `pthread_cond_wait` inside
20   `ncclProxyGetPostedOps` (proxy.cc:797), and the other progress threads polling at
21   proxy.cc:986. NCCL threads carry inherited names (`py_xla_execute` etc.) unless
22   `NCCL_SET_THREAD_NAME=1`; identify them by stack, not name.
233. **Map the stuck comm** (`pool_map.py`) — from the `ncclProxySaveOp` frame's `comm`
24   argument, print rank/opCount and the per-connection `proxyOps[]` table
25   (`count/freeOp/nextOps`) plus the shared pool's `nextOps`/`freeOps[tpLocalRank]`.
26   Deadlock state: everything `-1`/`0`.
274. **Prove client/service pool identity** (`pool_fingerprint_census.py`) — the same shm is
28   mapped at different VAs in the client and service roles, so never compare pool pointers;
29   compare the `freeOps[]` fingerprint. Also walks one partition's 2048 slots and
30   reconstructs the orphaned chains (leaked return batches Y-merge into shared suffixes).
315. **Measure the leak** (`freeops_deficit.py`) — for every in-use partition, walk the free
32   chain from `freeOps[r]` and report `2048 - length`. The number is an upper bound on
33   leakage: slots in a producer's private cache are also absent from the free list. On the
34   wedge this read 2048 / 830 / 446 / 702 across the four local ranks; the 2048 is a true
35   leak because that rank's producer cache was verified empty in step 3.
36 
37Root cause (fixed upstream in NCCL v2.29.3-1, commit 25368a7f78ba): the slot-return path in
38`ncclProxyGetPostedOps` used a weak `__atomic_compare_exchange_n` with a value-based retry
39condition (`while (swap != oldFree)`), which treats a spurious CAS failure as success and
40orphans the entire batch of freed slots. On aarch64 this compiles to ldaxr/stlxr with the
41stlxr success flag never tested; the producer's `__atomic_exchange_n(&freeOps[i], -1)` spin
42breaks the reservation while leaving the value unchanged, so leaks concentrate exactly at
43backpressure episodes. x86 `lock cmpxchg` cannot fail spuriously, which is why only the
44GB200 (Grace) fleet sees it.

208def adam_update(params, opt_state, grads, *, lr, b1=0.9, b2=0.95, eps=1e-8):
209    count = opt_state["count"] + 1
210    bc1 = 1.0 - b1 ** count.astype(jnp.float32)
211    bc2 = 1.0 - b2 ** count.astype(jnp.float32)
212 
213    def upd(p, m, v, g):
214        g = g.astype(jnp.float32)
215        m = b1 * m + (1.0 - b1) * g
216        v = b2 * v + (1.0 - b2) * jnp.square(g)
217        p = p - lr * (m / bc1) / (jnp.sqrt(v / bc2) + eps)
218        return p, m, v
219 
220    out = jax.tree.map(upd, params, opt_state["m"], opt_state["v"], grads, is_leaf=lambda t: isinstance(t, jax.Array))
221    new_params = jax.tree.map(lambda t: t[0], out, is_leaf=lambda t: isinstance(t, tuple))
222    new_m = jax.tree.map(lambda t: t[1], out, is_leaf=lambda t: isinstance(t, tuple))
223    new_v = jax.tree.map(lambda t: t[2], out, is_leaf=lambda t: isinstance(t, tuple))
224    return new_params, {"m": new_m, "v": new_v, "count": count}

4"""Child-side entrypoint that runs the #7344 wedge reproducer under the supervisor.
5 
6``GPUHangSupervisor`` spawns this via ``levanter.recovery.child``: it resolves
7``run_wedge_repro`` by module + qualname and calls it with the pickled config. The
8function brings up ``jax.distributed`` from the Iris task environment (the runtime
9does not do it for a raw entrypoint) and then runs the unmodified reproducer.
10

12#7344 branch. Detection is entirely environmental — the supervisor sets the XLA
13per-execution deadman in this process's ``XLA_FLAGS`` before spawn, so when the
14collective wedges the deadman ends the process in ``LOG(FATAL)`` and the

16to reproduce the wedge and show the deadman firing.
