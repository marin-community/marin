# Hero pipeline on GB200

The launcher uses the Hero model and kernels from Marin main `89ac0d7705`: d6144,
48 layers, 384 experts, top-8 routing, SM100 Flash Attention, device-initiated
ragged all-to-all, FP32 stored parameters with BF16 compute, compute-scaled MuonH
with symmetric GEMM and gate/router weight decay 0.02. Synthetic tokens isolate
pipeline execution from private training data. Optimizer state and block carries
are offloaded to pinned host memory. CUDA completion is synchronized after every
step while the intermittent unsynchronized NaNs remain under investigation.

## Checkout and prerequisites

Use Linux ARM64 GB200 hosts with a CUDA-13-compatible NVIDIA driver, working
NVLink/NCCL fabric, Python >=3.12,<3.14, `uv`, and public network access to GitHub,
PyPI, the NVIDIA package index, and PyTorch's CUDA wheel index. For the rack trial
reserve 16 four-GPU nodes in one NVL72 rack. Each node needs 120 CPUs, 890 GB RAM,
128 GB scratch disk, and a 7200-second task deadline. Use the scheduler's
opportunistic, preemptible low-priority queue.

The executable pin is `0da04acccf7b0842319a8668d71ccc697a7b10ec`, based on
main `89ac0d7705`. Its corrected eight-GB200 gate completed two finite updates
with losses 11.806337356567383 and 0.4912489652633667. All eight processes,
both GPU tasks and the coordinator exited zero. Both coordinator retry caps
were explicitly zero. The first attempt at this same pin also completed training, but its
coordinator was cancelled after discovering a default preemption retry cap of
1000; that attempt did not establish clean coordinator completion.

The executable is published on `codex/hero-gb200-pipeline` in
[PR #9662](https://github.com/marin-community/marin/pull/9662). Use:

```bash
git clone --branch codex/hero-gb200-pipeline https://github.com/marin-community/marin.git
cd marin
git checkout 0da04acccf7b0842319a8668d71ccc697a7b10ec
git rev-parse HEAD
```

Record the executable pin separately from later documentation-only commits
and record installed runtime versions. The H100 adapter gates ran at
`a1e3ab278eeb05bb645db641dd3e7dabedf90dbb`; the later installer, argument-parser
and run-naming changes preserve the valid MuonH recipe and runtime pins.
GB200 commands require `--processes-per-task 4` and `--optimizer muonh`.
The main recipe rejects AdamW before distributed initialization.

## Runtime

The experiment requires upstream JAXPP
`328f75a80cecf22c7cc030a82d8941d3c1e220b6` plus the checked-in
`runtime/jaxpp_host_startup.patch.gz` (decompressed SHA256
`d987c16ece399fe5eeb69d413703d549135635f19a57dc4b6c60cc0d1ea4b1a7`).
Upstream includes host memory propagation and asynchronous send-buffer lifetime
fixes. The remaining overlay schedules forward residual copies, infers pinned
host output placement, and compiles tasks on disposable startup inputs. It is
experimental, pending upstream support. Installation reinstalls clean pinned
source before applying the overlay and checks both the source pin and patch hash.

Run one pipeline per process. The startup overlay rebuilds a process-global
compiled-task cache; it does not support two concurrent pipeline instances.

Main's ragged transport requires Marin's ARM PJRT
`0.11.1+marin.708c3a4ec79c` and one process per GPU. This launcher intentionally
overrides JAXPP's declared JAX <=0.11.0 limit with JAX/JAXlib 0.11.1. The launcher
installs FA4 4.0.0b28, Cutlass DSL 4.6.2, QuACK 0.6.4, and main's CUDA-enabled
Torch 2.11.0+cu128. The previous eight-GPU gate installed CUDA bindings
12.9.7 through Torch; the JAX CUDA-13 and Torch CUDA-12.8 libraries coexist.
The earlier gate at `b8e1c1ff2763ac098e397bd78fa5995933cc140c`, using the same
upstream JAXPP pin and tracked overlay, completed two finite updates with losses
11.806339263916016 and 0.4912506341934204; all eight processes exited zero.
That earlier two-layer synthetic diagnostic validated execution and host-memory
placement for its recorded source and is separate from the cancelled attempt
at `0da04ac`. The corrected eight-GPU gate at `0da04ac` retained 48
startup task ABI records across all ranks with zero input memory-kind mismatches.
The full 48-layer rack memory footprint remains untested.
Current Quack helpers query Torch's CUDA device capability;
the pipeline extra's CPU-only Torch cannot run those helpers. A local dry run does not validate new
rack placements; require the GPU gate before each rack trial.

## Marin Iris commands

Run from the integration checkout. Both the CPU coordinator and GPU child use
Iris `batch`, its opportunistic, preemptible low-priority band. The launcher has
no priority override and requests one hard NVLink domain. It never exceeds 64
GPUs; run only one GB200 diagnostic at a time.

Use the SDK to set failure and preemption retry caps independently. The CLI's
`--max-retries 0` controls failure retries only.

```bash
export RUN_ID=pipeline-gb200-gate-$(date -u +%Y%m%d)-01
export SIZE=gate
uv run --no-sync python <<'PYTHON'
import os
from pathlib import Path

from iris.cli.connect import open_iris_client
from iris.cli.job import build_job_constraints
from iris.cluster.types import Entrypoint, EnvironmentSpec, ResourceSpec
from iris.rpc import job_pb2
from rigging.timing import Duration

resources = ResourceSpec(cpu=2, memory="8GB", disk="32GB")
with open_iris_client(config_file=Path("lib/iris/config/marin.yaml"), workspace=Path.cwd()) as client:
    job = client.submit(
        entrypoint=Entrypoint.from_command(
            "python", "-m", "experiments.grug.moe_hero_pipeline.launch_gb200",
            "--run-id", os.environ["RUN_ID"], "--size", os.environ["SIZE"],
        ),
        name=os.environ["RUN_ID"] + "-coord",
        resources=resources,
        environment=EnvironmentSpec(env_vars={"WANDB_MODE": "disabled"}, sync_packages=["marin-iris"]),
        constraints=build_job_constraints(
            resources.to_proto(), tpu_variants=[], replicas=1, target_cluster="cw-us-east-08a"
        ),
        replicas=1,
        max_retries_failure=0,
        max_retries_preemption=0,
        max_task_failures=0,
        existing_job_policy=job_pb2.EXISTING_JOB_POLICY_ERROR,
        timeout=Duration.from_seconds(54000),
        priority_band=job_pb2.PRIORITY_BAND_BATCH,
    )
    print(job.job_id)
PYTHON
```

The gate uses eight GB200s (two four-GPU nodes), PP2/EP4, two full-width layers,
sequence length 4096, batch 8, two microbatches, and two optimizer updates.
Require two finite rank-zero `pipeline_step` losses, `pipeline_complete` with
`steps=2`, and clean exit from all eight processes before the rack trial.

Use the same command with a unique `RUN_ID` and `SIZE=rack` after that gate
passes. The rack trial uses 64 GB200s (16 nodes), PP8/EP8, all 48 layers, sequence
length 4096, batch 128, 16 microbatches, and five updates. This is a new placement
and requires its own memory and numerical validation.

The coordinator waits up to 12 hours for the gang's first worker execution
timestamp. Iris's `BUILDING` state also includes queued `SchedulingGated` pods,
so it does not indicate admission. Each GPU task retains its two-hour execution
deadline, including setup and compilation, measured by Iris from execution start.
After the first worker starts, the coordinator waits up to two hours plus ten
minutes for completion and output finalization. Its 15-hour deadline includes
queue, execution, and startup grace. A queue or completion wait timeout cancels
the child and raises; actual worker failures propagate without retries. The
first rack submission timed out while queued and executed no GPU work. The
second rack obtained 64 GPUs and started some native processes, then failed
setup when a GitHub fetch failed and an install retry duplicated `--reinstall`.
The package-specific reinstall option avoids that duplicate flag on deployed
workers. Full 48-layer initialization, compilation and updates remain unvalidated.

## NVIDIA execution

The training executable has no Iris scheduler dependency. On each ARM host,
install the workspace environment and explicit runtime overrides from this
integration checkout. Some CUDA dependencies retain version lower bounds; this
is not a fully pinned standalone lock. Record installed package versions with
results. Ordinary `uv sync` resets the manual overrides, so use `--no-sync` for
subsequent commands or reapply the full installation sequence:

The JAXPP install reinstalls that package before applying the verified overlay.
Using `--reinstall-package jaxpp` also allows Iris runtimes to add their global
`--reinstall` option on a cache-recovery retry. The Iris worker setup wrapper retries an individual failed `uv pip install`
once with a task-local cache; a second failure remains fatal. It does not
repeat the overlay, toolchain setup, or training command. The manual shell
commands below have no automatic retry. Every node still needs GitHub access
to the exact Git commit and pinned PJRT wheel. Worker and training retries
remain disabled.

```bash
uv sync --all-packages --extra pipeline --no-dev
uv pip install 'jax[cuda13]==0.11.1' jaxlib==0.11.1 \
  'nvidia-nccl-cu13>=2.31.2' 'nvidia-cublas>=13.2.0.9' \
  'flash-attn-4[cu13]==4.0.0b28' 'nvidia-cutlass-dsl[cu13]==4.6.2' \
  'quack-kernels[cu13]==0.6.4'
uv pip install --index-url https://download.pytorch.org/whl/cu128 'torch==2.11.0+cu128'
uv pip install --no-deps \
  'https://github.com/marin-community/xla/releases/download/marin-xla-pjrt-20260915-708c3a4ec79c/jax_cuda13_pjrt-0.11.1%2Bmarin.708c3a4ec79c-py3-none-manylinux_2_27_aarch64.whl'
uv pip install --no-deps --reinstall-package jaxpp \
  'jaxpp @ git+https://github.com/NVIDIA/jaxpp.git@328f75a80cecf22c7cc030a82d8941d3c1e220b6'
uv run --no-sync python experiments/grug/moe_hero_pipeline/runtime/apply_overlay.py
uv run --no-sync python -c \
  'from iris.cluster.setup_scripts import cuda_toolchain_setup_script; print(cuda_toolchain_setup_script())' \
  > /tmp/pipeline-cuda-toolchain.sh
IRIS_VENV="$PWD/.venv" IRIS_WORKDIR="$PWD" bash /tmp/pipeline-cuda-toolchain.sh
export PATH="$PWD/.venv/bin:$PATH"
export WANDB_MODE=disabled JAX_PLATFORMS=cuda JAX_ENABLE_PGLE=false
export XLA_PYTHON_CLIENT_ALLOCATOR=cuda_async XLA_PYTHON_CLIENT_PREALLOCATE=false
export XLA_PYTHON_CLIENT_MEM_FRACTION=0.85 JAXPP_DISABLE_SCHEDULE_TASK_FUSION=1

uv run --no-sync python -c \
  'import torch; assert torch.cuda.is_available(); print(torch.__version__, torch.cuda.get_device_capability())'
```

Launch one process per GPU, with the distributed rank arguments below on all
ranks. The Iris wrapper is one way to provide those coordinates. Start with the eight-GPU gate on two four-GPU nodes:

```bash
python -u -m experiments.grug.moe_hero_pipeline.pipeline_smoke \
  --coordinator-address "$COORDINATOR_ADDRESS" --num-processes 8 \
  --process-id "$GLOBAL_RANK" --local-device-id "$JAX_LOCAL_DEVICE_ID" \
  --main-hero-recipe --processes-per-task 4 --optimizer muonh --schedule standard_1f1b \
  --stages 2 --expert-axis-size 4 --microbatches 2 --batch-size 8 \
  --sequence-length 4096 --diagnostic-layers 2 --steps 2 \
  --offload-opt-state --offload-activations --park-state-during-warmup \
  --synchronize-devices-after-step
```

Require rank zero to emit two finite `pipeline_step` losses and
`pipeline_complete` with `steps=2`, plus exit code zero from all eight processes.
The gate does not validate the full rack's memory footprint. Only after it
passes run the 64-GPU command:

```bash
python -u -m experiments.grug.moe_hero_pipeline.pipeline_smoke \
  --coordinator-address "$COORDINATOR_ADDRESS" --num-processes 64 \
  --process-id "$GLOBAL_RANK" --local-device-id "$JAX_LOCAL_DEVICE_ID" \
  --main-hero-recipe --processes-per-task 4 --optimizer muonh --schedule standard_1f1b \
  --stages 8 --expert-axis-size 8 --microbatches 16 --batch-size 128 \
  --sequence-length 4096 --steps 5 --offload-opt-state --offload-activations \
  --park-state-during-warmup --synchronize-devices-after-step
```

Set `COORDINATOR_ADDRESS` to rank zero's host and an unused port. Number nodes
from zero and physical GPUs within each node from zero through three:
`GLOBAL_RANK=4*NODE_RANK+LOCAL_RANK`. Gate global ranks are 0 through 7; rack
ranks are 0 through 63. Run the command once per GPU on every selected node.

If each process sees all four physical GPUs, set `JAX_LOCAL_DEVICE_ID=$LOCAL_RANK`.
If the scheduler isolates one GPU with `CUDA_VISIBLE_DEVICES`, JAX sees that GPU
as visible ordinal zero, so set `JAX_LOCAL_DEVICE_ID=0` regardless of physical
local rank. Preserve the scheduler's GPU isolation. The scheduler must place these processes
inside one NVL72 rack
and use its low-priority queue. No production checkpoints or private datasets
are read or written.
