# Pi scenarios in vendored SkyRL

`vendor/harbor` captures Pi model calls and executed tool observations in memory, with a validated trial ID and policy step. `vendor/skyrl` consumes that capture through its shared RolloutEngine task worker. Neither worker logs nor saved sandbox files supply missing trajectory evidence.

The nested SkyRL lock installs `harbor` from the checked-in sibling tree through `vendor/skyrl/harbor`. The launcher includes Harbor's source and package metadata in the hash-verified runtime bundle. CPU and GPU workers therefore install the same edited Harbor package. Do not replace the local lock source with a stale upstream Harbor revision: that bypasses Pi capture even when both vendored directories exist.

The reviewed scenario selectors now include all six target tracks plus the separate `verifier_grpo_base` baseline. Turn-mixture, nonzero-prefix handoff, and critique/revision now have bounded GPU-serving physical smokes; their method-specific GPU optimizer gates remain open. The launch recipes under `vendor/skyrl/cloud/iris/configs/pi_*_smoke.yaml` still require fresh job, attempt, and output identities. They allow four model turns: the vendored RolloutEngine cancels Pi at the configured turn cap, so a two-turn limit can stop a tool follow-up before validated capture is returned. Per-turn distribution and GRPO training use the exact served prompt and sampled response. Distribution teacher requests use unique turn IDs while group admission retains the physical task and repetition IDs. The teacher-trace path keeps private teacher labels apart from student samples; grades come from the task verifier. Worker-owned Pi sandbox attempts stream fixed-schema phase journals. Pi attempts do not upload raw sandbox artifacts by default.

The standalone work completed one checkpointed teacher-trace update, one verifier-GRPO update, and one top-K teacher-distribution update. See [the standalone smoke record](https://github.com/marin-community/MarinSkyRL/blob/1fce8f26/docs/pi-scenario-smokes.md) for trial counts and limits. Those jobs ran the standalone revision. Vendored results and remaining gates are below. AI-judged GRPO, turn-mixture DAgger, student-prefix teacher completion, and critique-to-revision still need their own live optimizer gates; a GPU-serving smoke, ETL rows, and a trainer update are separate claims.

## Six target scenarios and their evidence gates

The design has **five method families and six target tracks**: turn-mixture DAgger and student-prefix → teacher completion are different execution protocols. Grader-gated teacher trace is a *filter on track 1*, not a seventh target. **Verifier-GRPO is a separate, non-target baseline scenario**, not AI-judged GRPO: its reward is the task verifier's grade, whereas track 3 optimizes an independent judge's score. Their trials, groups, gradients, and checkpoints cannot substitute for each other.

For this inventory, **CPU physical E2E** means installed Pi actually ran in a Docker task sandbox, with in-memory capture passing the shared worker and (where stated) a real verifier; constructed fixtures, mocked HTTP, and tiny-policy backprop by themselves do not count. **GPU physical E2E** means a GPU-served model actually drove Pi through a task, evidence validation, grading where enabled, and ETL. A GPU *optimizer gate* additionally needs admitted physical training rows, nonzero method-appropriate gradient, weight sync, and checkpoint. A serving smoke, an ungraded trial, and a CPU optimizer step are different claims. An E2E check is not proof of quality or repeatability.

- **Critique/revision:** one GPU student attempt, one independently served private GPU teacher critique, one tool-free GPU student revision, and one revision SFT row. A second bounded physical attempt also graded 1; these two smokes do not establish multi-step repeatability.

The first imitation attempts exposed real blockers rather than passing gates: Pi's default thinking mode produced length-limited reasoning-only student completions (invalid submissions, no teacher-executed turn), and Marin's serving dashboard exposes `/tokenize` at the root rather than `/v1/tokenize`. Failed setup, invalid submissions, and ETL failures were **not** admitted as reward-0 training samples by these smokes. These are serving/worker/grade/ETL checks, **not** optimizer updates, weight sync, checkpoints, restart, quality, or production image/ingress approval.

### Imitation execution scheduling (GPU prefix-1 handoff passed; CPU prefix-0 only)

Keep the execution decision separate from the expert-label contract: at **every** visited pre-action Pi turn, the teacher supplies one private action label for supervised learning. The scheduled quantity determines only **who executes** that turn. A completed Pi rollout may contain many turns; neither schedule decides whether to grade a completed rollout or whether to ask the teacher for labels. Production preflight now accepts the turn-mixture and critique presets with distinct pinned teachers and fail-closed controls. Their first CPU Pi/Docker routing trials used scripted completions; the later GPU-served physical trials passed without a GPU optimizer update. The prefix preset passes config preflight and a teacher-only physical CPU grading trial; its separate GPU-serving prefix-1 handoff passed, but a GPU optimizer step, restart, and a model-backed CPU handoff are still separate gates.

The two execution controls use typed schedules measured in **rollout/update iterations**, not Pi turns or optimizer minibatches. Values are evaluated from the leased policy step at the start of each iteration and clamped after `duration_iterations`. Turn-mixture DAgger's linear schedule has the paper's first three values `1.0, 0.8, 0.6` and then stays at `0.6`:

```yaml
scenario:
  preset: dagger_pi_turn_mixture_base
terminal_bench_config:
  installed_agent:
    turn_mixture_schedule:
      teacher_execution_probability:
        scheduler: linear
        start: 1.0
        end: 0.6
        duration_iterations: 2
```

Each physical trial pre-samples independently drawn Bernoulli executors before Pi starts, seeded by its trial identity and leased policy step. A retry of that lease replays the same plan; student actions or grades cannot change it. The plan selects who acts at each visited turn, not which states get private expert labels. The teacher-executed action itself is the label for teacher turns, while student-executed actions have a separate private teacher label at the same frozen pre-action state. An opt-in CPU Pi/Docker trial sampled a plan with student then teacher, executed a student bash call and teacher completion, checked both private labels and the real verifier grade. Its scripted replies establish routing, not policy sampling or optimizer training; the subsequent GPU-served student→teacher trial passed the same attribution and verifier gates with distinct pretrained models.

The critique preset binds a per-trial feedback principle and independently routed teacher to the same worker. Its opt-in CPU Pi/Docker trial executed one scripted student attempt, obtained a private teacher critique under the agent's request-correlation ID, and graded one scripted student revision. Harbor rejects missing or mismatched private feedback before training. Constructed worker-to-trainer tests reach tiny-policy SFT updates for both tracks; later GPU-served physical rollouts passed, but none of these trials updated weights.

Prefix takeover is a **separate scenario**, not a DAgger mode flag: sample one integer student-prefix length at the start of a physical rollout, execute student actions until that turn, then teacher actions thereafter, without switching back. The student prefix still gets expert labels. Its current config uses a named discrete sampling distribution and a linear schedule for its upper bound, using `scheduler/start/end/duration_iterations` measured in rollout iterations. For example, scheduling the upper bound of `uniform_int(min=0, max=scheduled_value)` toward longer prefixes would be an **explicit design choice**, not a verbatim reproduction: the paper specifies approximately `Uniform{0, …, 40}` and a shift toward longer prefixes but does not fully spell out that shifting rule. The provisional Hydra preset currently uses `end: 4` under `terminal_bench_config.installed_agent.prefix_schedule`; this is a tested scheduler contract, **not** a paper-specified distribution or an approved default. Teacher-executed turns now enter the shared engine's model session for grading, while private teacher labels stay out of that session. A separate GPU-served prefix-1 handoff passed grading and ETL. Settle the intended bound and validate restart behavior before publishing a default.

These scenario schedules are distinct from `trainer.policy.optimizer_config.scheduler` (currently `constant_with_warmup` or `cosine` with `num_warmup_steps`). Optimizer training steps and rollout/update iterations are not interchangeable, especially on restart. Persist the iteration, scheduled value, sampled executor/prefix, teacher labels, and replay identity; admission must not turn failed or ungraded attempts into training rows. The reported paper uses fresh mixed batches at each iteration and filters **valid submissions**, not merely successful ones. Keep submission validity separate from verifier grade and optional replay policy. See [Revisiting DAgger in the Era of LLM-Agents, §3 and Appendix F](https://arxiv.org/abs/2605.12913).

### AI-judged GRPO: CPU integration and GPU-serving smoke, no GPU optimizer step

Select `scenario.preset: rlaif_pi_base` and configure `environment.task_sessions.pi_judge` with an independent model alias, its 40-character pinned revision, an HTTPS `/v1` endpoint, an explicit judging principle, `prompt_revision: rlaif_judge_v1`, and `auth: file:/run/rigging/secrets/PI_JUDGE_TOKEN`. The judge's model/revision are *declared* provenance, not remote weight attestation: verify the separately operated endpoint's actual revision before a live run. At Iris submission, supply `PI_JUDGE_TOKEN` through the launcher secret source; the launcher delivers it as an Iris mounted application-secret file, **not** in task environment values or the source task pack. Locally, `auth: env:PI_JUDGE_TOKEN` is available for isolated tests, but Iris submissions reject it. This is distinct from `environment.task_sessions.remote_judge`, which supplies task grading.

The worker refuses ungraded or failed trials, a missing judge, or identity mismatches before judging. The external judge receives only the validated executed student transcript, not private grader outcomes or teacher labels; it must return one exact binary score and a request ID for its configured model. A trial is judged **once** even if its Pi trajectory has several exact served turns. ETL trains on each turn's sampled tokens/logprobs under the *same physical trial identity*; turn rows do not become independent GRPO group members. The private task-verifier score stays in its separate channel. The CPU tests include a mixed-judge-score optimizer step but use constructed evidence and a fake/HTTP-fixture judge. A separate opt-in Docker test runs real Pi and CPU policy completions through task grading, then scores that physical trial with a scripted HTTP judge: its verifier reward is 1, judge reward is 0, and exact sampled tokens/logprobs survive ETL.
